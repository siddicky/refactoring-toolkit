Context: pi-dynamic-workflows (pi-DW) is a Pi CLI extension implementing "script-as-orchestrator" dynamic workflows (same idea family as Claude Code dynamic workflows and the ODW fork we already evaluated). Our consensus plan REJECTED the script-as-orchestrator **interpreter** (its SQLite/file replay cache = second source of truth vs. "dex attributes are source of truth") and RECORDED the script→dex-steps **compiler** as the coherent v2 boundary (plan line 197). This lane asks what the most mature implementation of that pattern does, and whether anything it does changes our verdict.

## 1. The authoring surface: model-written `execute(context)` JS in a Node vm realm

### 1.1 What the script is and how it executes

- The host model (Pi) writes the workflow; the `workflow` tool accepts `script` or a saved `name` (`src/workflow-tool.ts:31, 41`). Script shape: first statement MUST be `export const meta = { name, description, phases }`, then the body (`src/workflow.ts:2011-2071`, `parseWorkflowScript`). `meta` must be a *literal* — the AST evaluator allows only plain object/array/literal/negative-number nodes; spread, computed keys, methods, template interpolation, and `__proto__`/`constructor`/`prototype` keys all throw (`src/workflow.ts:2073-2109`).
- Execution: `vm.createContext({...projectGlobals})` (`src/workflow.ts:1802`), wrapped as `DETERMINISM_PRELUDE + (async () => { body })()` and run via `new vm.Script(wrapped).runInContext(context)` (`src/workflow.ts:1810-1817`).
- Injected globals (`src/workflow.ts:1774-1798`, assembled via the capability contract at 1799-1801): `agent, parallel, pipeline, workflow` (nested saved runs), `verify, judgePanel, loopUntilDry, completenessCheck, retry, gate, checkpoint, log, phase`, plus values `args, cwd, process: {cwd()}, budget` and a `console` shimmed to `log`. Host built-ins are deliberately NOT injected: "Object/Array/JSON/Math/Date/Promise/Set/Map/etc. come from the vm realm itself — we deliberately do NOT inject host built-ins, whose .constructor would be the host Function (a determinism-guard bypass)" (`src/workflow.ts:1804-1807`).
- `require`/`import`/fs/network are banned by omission — nothing that reaches them is injected into the realm. The project itself states vm is **not a security boundary**: "an injected bridge function's `.constructor` is still the host Function, so a determined script could bypass this. The guard is best-effort against ACCIDENTAL nondeterminism from trusted (user / guided-LLM) scripts" (`src/workflow.ts:524-527`; same caveat in README:299 "VM realm (for determinism, not a security boundary)").

### 1.2 Determinism — three layers

1. **Parse-time blocklist**: regex `/\bDate\s*\.\s*now\b|\bMath\s*\.\s*random\b|\bnew\s+Date\s*\(\s*\)/` fails the run before execution (`src/workflow.ts:514`, enforced at `2012-2018`). Labeled "author hint (fast feedback)" — prelude is the real enforcement.
2. **Runtime prelude** (`DETERMINISM_PRELUDE`, run inside the realm before the user script, `src/workflow.ts:529-546`): `Math.random` → throws; `Date.now` → throws; `Date()`/`new Date()` no-arg → throws; `new Date(arg)` still works via `Reflect.construct`. Uses the *realm's own* Math/Date/Reflect to avoid introducing host-Function escapes.
3. **Realm isolation** (above): no host intrinsics in the context object.

Rationale, verbatim: neuters "the nondeterministic builtins that would break resume (they'd make a re-run produce different values than the cached journal)" (`src/workflow.ts:517-519`). Determinism is in service of the replay cache, nothing else. Also: the agentType registry is snapshotted ONCE per run "so two agent() calls can't observe a mid-run edit (determinism)" (`src/workflow.ts:576-578`).

### 1.3 What script-as-orchestrator buys (honest comparison to our hand-written TS dex flows)

What it genuinely buys:

- **Expressiveness / authoring cost**: one script = the whole orchestration; arbitrary control flow (loops via `loopUntilDry`, conditionals, try/catch), data plumbing through plain JS variables, composable quality stdlib (`verify`, `judgePanel`, `gate`, `completenessCheck` — `src/workflow.ts:1774-1798`; worked examples in `skills/workflow-authoring/examples/`). Our v1 gets this for exactly ONE flow (`flows/port-project.ts`); a new workflow = writing a new TS flow by hand.
- **Per-run authoring**: the model writes bespoke orchestration per request ("audit every route under src/routes/", `/deep-research`, `/code-review` — README:123-133). No pre-built flow needs to exist. This is the real product moat of the pattern; our toolkit has no equivalent surface.
- **Saved composable workflows**: `/workflows save <name>` persists the latest script as a command; nested `workflow(savedName, args)` runs inline sharing the parent's limiter/counters/budget, one level deep (`src/workflow.ts:1391-1436`); a saved workflow shadows a built-in of the same name (README:152).
- **Context economy**: "Intermediate work stays in script variables instead of filling your chat context" (README:17).

What it costs (and dex gives us structurally):

- **Second source of truth**: resume correctness depends on (a) a deterministic script re-run and (b) the file-based journal cache (`journal[]` of results in `<runId>.json`). Nothing about agent-call results lives in a durable substrate; the journal *is* the record of paid calls. This is exactly the architecture our consensus rejected (plan line 197: "never as an interpreter-over-cache").
- **Crash window inside a call**: subagents are in-memory by default (persistAgentSessions is opt-in, README:265); a host-process SIGKILL loses every in-flight agent call (only *completed, journaled* calls survive). Their own durability claim stops at "a process-crash/atomic-rename protocol, not a promise of power-loss durability on every filesystem" (`docs/run-storage.md:18`). There is no server/worker split, no fencing, no worktree reconcile. Our AC1 (SIGKILL of server AND workers, zero re-invocation of completed files, op-ID dedup across a killed commit window) is strictly beyond anything in this codebase — their equivalent is "re-run whatever didn't finish, from cache for what did."
- **Determinism tax on the author**: the model must write to the banned-API contract and to lexical call-order discipline (insert/remove/reorder of an `agent()` call invalidates the cached prefix from that point — README:314). Ours moves that burden into the compiler/step layer.

## 2. Journaled replay: mechanisms

### 2.1 Storage protocol: versioned head + append-only events log

- Files: `<runId>.json` (versioned index head) + `<runId>.json.events.jsonl` (append-only change log) + `.json.bak` (last good head mirror) (`docs/run-storage.md:5`, `src/run-record-store.ts:221`).
- Head holds routing/status fields, compact agent counts/usage, and `bytes` (committed log boundary), `sequence`, `generation` (uuid), `hash` (SHA-256 chain tip) (`src/run-record-store.ts:371-379`). Scripts, args, journals, logs, agent rows, and results live in log *deltas*, not the head. Unknown format versions fail closed (`docs/run-storage.md:5`).
- **Commit protocol** (`docs/run-storage.md:11-17`, `src/run-record-store.ts:352-382`):
  1. acquire a short per-run writer mutex — a `link(2)`-based atomic claim with dead-owner reaping guarded by a per-incarnation reaper mutex (`src/run-persistence.ts:401-454`);
  2. derive a delta: changed scalars/objects and changed array cells only (unchanged completed journal/agent rows are NOT rewritten — bounds write volume);
  3. discard bytes beyond `head.bytes` (removes any uncommitted tail from a crashed writer, `src/run-record-store.ts:366-369`), append the chained entry `{generation, sequence, previous, delta}` with `flush: true`;
  4. **atomic rename of the new head = the commit point** (`src/run-record-store.ts:379`), then best-effort `.bak` refresh.
- **Crash/integrity semantics**: crash before step 4 → readers ignore the uncommitted tail, next writer truncates it. A truncated or hash-invalid *committed* log **fails closed** "rather than silently replaying an older paid-call prefix"; only a corrupt/missing head falls back to `.bak` (`src/run-record-store.ts:301-308`, `docs/run-storage.md:18`). Chain validation on hydrate: generation, monotone sequence, `previous` hash linkage, byte-boundary check (`src/run-record-store.ts:269-296`).
- Journaling of a paid call happens the moment a call finishes with a real result: `onAgentJournal?.({index, runId, hash, result, model, storeDelta})` (`src/workflow.ts:1179-1190` for live agents; `1770` for checkpoints; `1733` for durable checkpoint responses). The manager funnels this to disk via a deferred persist timer (`workflow-manager.ts:1612-1616` — "That callback only fires from onAgentJournal"). Empty-text results are `AGENT_EMPTY_OUTPUT` recoverable failures and are **never journaled** (`src/workflow.ts:1170-1175`; README:316), so a resume re-runs exactly that one call plus its lexical suffix.

### 2.2 Positional call-index replay

- `callIndex = state.callSeq++` is assigned at *lexical* call time, synchronously, before the concurrency limiter (`src/workflow.ts:890-892`), with a synchronous slot reservation so a parallel fan-out can't overshoot the agent cap (`src/workflow.ts:916-925`) — "callIndex/agentCount must stay lexical for replay-key stability."
- Cache key: `${runId}:${callIndex}` (`src/workflow.ts:914`) — namespaced because nested `workflow()` frames restart their own callSeq at 0 (`src/workflow.ts:902-913`).
- Cache *validity* additionally requires a **call hash**: `hashAgentCall(prompt, modelSpec, phase, options, agentDefKey, cwd, isolation)` (`src/workflow.ts:893-901, 2264-2295`) — editing an agent .md definition, schema, model, or prompt invalidates that call's cached result.
- **Longest-unchanged-prefix semantics**: replay only while `callIndex < state.firstMiss`; the first genuine miss (no entry, hash changed, or previously-empty-output) sets `firstMiss` and everything from there runs live (`src/workflow.ts:503-508, 927-969`). Mismatched calls re-run — no crash (README:314).
- Replay applies the journaled `storeDelta` additively so later live agents see a consistent shared store (`src/workflow.ts:959-963`); threaded calls set `resumeBarrierReached`, disabling replay for the rest of the run (`src/workflow.ts:936`).

### 2.3 resumeFromRunId — edit-and-resume

- `resume(runId, {script})` (`workflow-manager.ts:1852-2160`) loads the persisted record, re-reads it **under the run lease** and fails closed if it changed since the pre-lease read (`workflow-manager.ts:1876-1886` deepStrictEqual guard), hydrates `resumeJournal` as `Map<`${runId}:${index}`, entry>` (`workflow-manager.ts:2143`), and re-runs the *possibly edited* script. Unchanged calls replay at zero tokens; edited/new calls re-run (README:80, 314-316; model-facing guidance string at `src/workflow-tool.ts:465`). Ghost agent rows (in-flight at pause) settle to `skipped` with an interrupt cause and are re-seeded so the snapshot never regresses to an empty fleet (`workflow-manager.ts:1986-2010`).
- Cross-process safety: pid-liveness-checked lease files with stale-lock reclaim (`src/run-persistence.ts:734-766`); limits fixed at run start (tokenBudget, maxAgents increase-only on resume, timeout, concurrency, retries) persist and resume re-applies *these* values, never current defaults (`src/run-persistence.ts:153-207`; README:249). Cumulative token budget across pause/resume via `initialTokenUsage` seeding (`workflow-manager.ts:306-310`).

### 2.4 Pause/resume + auto-resume on provider usage limits

- Pause: `pause()` → status `paused` with journal preserved — deliberately NOT `failed` (`workflow-manager.ts:606`, pause classification block at `1300-1349`). A paused run is never evicted from memory or disk retention (`src/run-persistence.ts:276-280`).
- Provider usage-limit: `PROVIDER_USAGE_LIMIT` is classified `recoverable: false` specifically "so the run checkpoints" instead of retrying into the wall (`src/errors.ts:209-215`). The manager's catch converts it to `status: "paused"` with `pauseReason: "usage_limit"` + the provider's verbatim `resetHint` (e.g. "Resets in ~3h") (`workflow-manager.ts:1345-1360`). Tradeoff, documented: any sibling still in flight when the quota hit is aborted un-journaled — its work re-runs (double-paid) on resume (`src/workflow.ts:1856-1863`).
- `UsageLimitScheduler` (`src/usage-limit-scheduler.ts`): a deliberately standalone module consuming only the manager's public surface (`usage-limit-scheduler.ts:17-22`). Parses human reset hints — relative ("1h30m", "in 90s") and absolute ISO ("It will reset at 2026-09-17 13:20:54 +0800") — into a delay (`:104-140`); arms `resume()` with ±10% jitter (so a shared quota event doesn't wake a thundering herd, `:61-67`), exponential backoff (floor 1 min, fallback 5 min, ceiling 6 h), max 5 real attempts per pause-cycle, and a separate 10-refusal cap for structurally-refused resumes (`:45-95`). The attempt counter is persisted through the manager so a restart doesn't reset the give-up cap (`src/run-persistence.ts:195-200`, #207).
- **Checkpoint** (human gate): `checkpoint()` is a journaled, replayable gate — the human answer is journaled as a call result (`src/workflow.ts:1733, 1770`); resume-identity hash covers prompt/options AND `kind/checkpointId/payload/default/headless/timeoutMs`, so changing any of them invalidates a stale cached answer (README:333). Durable-form checkpoints (`{kind, checkpointId, payload}`) suspend the run durably with at-most-once response application (`src/workflow.ts:1665-1733`, `workflow-manager.ts:1862-1877`).

### 2.5 What is portable to dex-based orchestration WITHOUT breaking single-source-of-truth

- **Portable (pattern-level)**: call-hash → step-input-hash; edit-and-resume as compiler graph-diff; usage-limit auto-resume as a trigger; checkpoint as a durable human-gate step; evidence-stream hash-chaining discipline. Details in the VERDICT table.
- **Not portable as-is**: the journal cache itself. In pi-DW the journal is the *only* record of paid calls; in ours, dex steps/attributes/dispatch log are. Any replay-from-cache mechanism would duplicate truth. The honest framing: pi-DW's replay answers "which call am I?" positionally because the interpreter must *re-derive* the call sequence by re-running the script; dex answers it *by construction* (each step has a durable identity). Our equivalent of "only the first changed call and everything after re-runs" is compile-time graph diffing — feasible precisely because compilation is deterministic.

## 3. Parallelism model

- Caps: `MAX_AGENTS_PER_RUN = 1000`, `MAX_CONCURRENCY = 16` (`src/config.ts:7, 15`); per-run `concurrency` clamped to [1,16] (`src/workflow.ts:2354-2357`); default = `hardwareConcurrency - 2` clamped (`src/workflow.ts:613-615`). A single in-process async limiter (`limiter(async () => ...)` at `src/workflow.ts:1005`) is the only scheduling mechanism.
- `parallel(thunks)` (`src/workflow.ts:1313-1350`): `Promise.all` over indexed thunks; input order preserved in the result array. Per-slot error isolation: recoverable failure → `null` in that slot + log; non-recoverable (budget/agent-cap) → rethrows and halts the run, with **batch-scoped cancellation** via `AsyncLocalStorage` (`fanoutScope`) so a breached fan-out cancels only its own descendants, not sibling fan-outs (`src/workflow.ts:1319-1324`).
- `pipeline(items, ...stages)` (`src/workflow.ts:1352-1389`): each item flows through stages sequentially, items concurrent, same error model.
- Exhausted-recoverable-failure semantics: a fleet-wide all-null result still reports `completed`, with a prominent "produced no usable results" warning naming the empty agents (README:247).
- Worktree isolation: per-agent `git worktree add -b pi/wf/<id>` under `<repo>/.pi/worktrees/<name>` (`src/worktree.ts:54-77`) with best-effort cleanup of a failed `worktree add` (`:96-126`). **"Results are NOT auto-merged. The path is logged"** (`src/worktree.ts:2-3`); kept by default *for the human/parent to merge* (README:81, `keepWorktree: false` deletes, for tests).

**Comparison to our per-file dispatch over a 2-worktree pool**: pi-DW buys 16-way fan-out by having *no* write-correctness story — merge is punted to a human, there is no exactly-once commit, no integration branch, no queue verification of merged output. Ours is the opposite trade: concurrency capped by design (2 worktrees, single enforcement point, plan line 108) but every parallel writer lands through the sole-committer op-ID step into one `integration` output that the queues actually verify (plan lines 74-80, 86). These are different products: pi-DW fans out *read/analyze/propose* tasks; ours runs *writes-to-one-output-project*. Nothing in their model strengthens our write path; the only transferable idea is that a durable "slot reservation before any await" discipline (`src/workflow.ts:916-925`) is unnecessary for us — dex scheduling owns dispatch.

## 5. Ruling: does journaled replay change the v2 "compiler not interpreter" boundary?

**No — it hardens it.** Three observations from the code:

1. The replay cache exists *only because* the interpreter must re-run the script to re-derive positional call indices; determinism enforcement (§1.2) exists *only to protect* that cache. Strip the interpreter and the cache loses its reason to exist — dex step identities replace positional indices, and the call-hash (VERDICT #3) becomes a reconcile-time input-hash attribute. pi-DW's own docs concede the durability ceiling: in-flight calls are lost to a host crash, the protocol is "not a promise of power-loss durability" (`docs/run-storage.md:18`), and there is no cross-process worker, fencing, or worktree reconcile — i.e., nothing here challenges our SIGKILL-proven dex substrate; it operates strictly below it.
2. The valuable capability — edit-and-resume where unchanged work replays free (VERDICT #4) — transfers to the compiler *better*: deterministic script→step-graph compilation makes "re-run from first change" a structural graph diff resolved through our existing op-ID/marker/reconcile machinery, with dex attributes remaining the sole source of truth. The script layer stays exactly where the consensus put it: a future authoring/compiler boundary (plan:197), never an interpreter-over-cache.
3. The parallelism moat (16×1000) is real but orthogonal: it buys fan-out for read/propose work by having no merged-output correctness story at all (VERDICT #11). Our design constraints exist because we produce one verified output project — not a limitation pi-DW solves.

Net new adoptable items for the roadmap: usage-limit auto-resume (ADOPT, #7), step-input-hash reconcile evidence (ADAPT, #3), run-config freeze-on-start (ADAPT, #6), human-gate step with identity-validated response (ADAPT, #8), loopUntilDry termination rule as a cap-complement (ADAPT, #12), all-null warning in the metrics render (ADAPT, #14). Total ≈ 2–3 days spread across Phase 2 hardening, Phase 3+, and v2.
