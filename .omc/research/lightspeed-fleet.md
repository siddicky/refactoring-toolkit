## 1. Borrowed compute (lightspeed-envd, Incus, power states, VFS transfer)

### The dial-home model (their headline; directly relevant to a no-inbound shop)

- `crates/environment-daemon/src/registration.rs:1-3` — module doc: "Outbound registration: dial the environment gateway, prove the daemon identity, and serve reverse-dialed data connections for as long as the control connection lives." The daemon **never listens inbound**; control is one outbound WebSocket, and every data connection is another *outbound* dial (`registration.rs:416`, `run_data_connection`).
- `README.md:136-138`: "it dials in and registers itself, so NATed VMs, Kubernetes pods, and benchmark sandboxes need no inbound address." `docs/documentation/environments/bring-your-own-compute.md:102-104`: "This command does not start a passive listener on the machine."
- Admission: a **registration key** is minted per-universe in the UI (BYOC doc :59-81; persistent vs ephemeral identity modes; active-environment limit). After first registration the daemon holds its own persistent identity (`receipt.json` + private key in a 0700 state dir, BYOC :43-57, :106-119); a closed identity is **spent** (BYOC :166-169). Reconnect backoff 1s→60s with stable-session reset (`registration.rs:28-33`); terminal rejections exit non-zero so an orchestrator sees them (`registration.rs:13-15`).
- Three compute sources (`docs/documentation/environments/overview.md:37-41`): **Registered** (daemon dials out; you own the machine), **External** (runtime dials a daemon you expose; dev shortcut, unauthenticated — loopback only, BYOC :185-201), **Provisioned** (Incus provider).
- **Incus provider** (`crates/environment-provider-incus/`): separate process; HTTPS client-cert to Incus; operator-configured templates (immutable image fingerprint required — `incus-vms.md:52-55`); relays envd ops into each VM; no DB access and no session workflows (`incus-vms.md:19-22`). Config: `crates/environment-provider-incus/src/config.rs:14-49`. **Caveat**: its controller and guest-daemon listeners "currently have no application-level authentication" (`incus-vms.md:23-25`) — protected-network-only.
- **Power states + idle policy**: Incus exposes running/paused/stopped (suspended is in the protocol but not Incus) — `power-and-cleanup.md:7-16`. Idle policy is **staged and monotone** (pause_after → suspend_after → stop/close), the reaper only fires with "no running work" (tracked processes/jobs keep it awake; stray processes don't), later stages do **not** auto-escalate once lowered, and any use of a paused/stopped env requests a **wake-on-use** with the tool call waiting for readiness (`overview.md:97-106`, `power-and-cleanup.md:31-45`). Code: `crates/environments/src/tests.rs:403-504` (monotone stage validation, desired-vs-observed power divergence, reconcile lists).
- **VFS↔environment transfer** (`docs/documentation/environments/vfs-transfer.md`, `README.md:141-142`): `vfs_materialize` / `vfs_capture` between the persistent VFS and the machine FS — whole-tree atomic replace (destination-only entries removed, siblings preserved), `on_existing: error` option, symlinks rejected, capture publishes an immutable snapshot first and re-checks workspace revision (concurrent-edit → `published: false` with snapshot retained), whole-file reuse + bounded streaming, Linux + macOS.
- Architectural cost of the dial-home model: **exactly one environment-gateway process per deployment** owns live registered connections, lifecycle reconciliation, and idle power management; it does not scale horizontally today (`networking-and-ingress.md:22-29`).

### Comparison to our 2 local worktrees

Our pool is process-local (`src/git/worktree.ts`, epoch+base-SHA leasing over `git worktree`s — consensus plan :53-54, :108). Lightspeed solves a different problem: it separates the *harness* (durable workflow, no OS) from *compute* (borrowed machines), so "one worker manages hundreds of agents" (`README.md:33-34`). We deliberately fuse harness+compute in one local process; our equivalent of "borrowed compute" is a leased directory, not a machine.

Would their model let a fleet of agent worktrees span machines a company already has? **Yes — that is precisely what the registered-daemon path is for**: any workstation/VM/pod behind NAT with outbound HTTPS/WebSocket becomes fleet capacity, with no VPN inbound hole and no cloud provider. For a specialist-hosting shop this is the single most relevant idea in the repo: fleet capacity = machines the company already runs, admitted by a key, dialing the one gateway. The gap for us: dex already has a `worker_target` address (`BUILD_NOTES` §Environment, `DEX_WORKER_TARGET`), i.e. the *inverse* topology — the orchestrator dials the worker. Inverting that (worker dials dex) is a dex-core concern, not a toolkit concern; at 2 local worktrees we do not need it for the demo, but it is the honest answer to "how does this scale across our floor?" in the room.

## 2. Security posture

- **Encrypted secrets at rest**: `crates/store-pg/src/auth.rs:3-15` — "Secret values are sealed with AES-256-GCM before insertion. The AAD binds each ciphertext to its universe, secret id, and secret kind, so rows cannot be swapped or relabeled without failing decryption." Cipher + AAD construction at `auth.rs:33-55` (`secret_aad` = `{universe}/{secret_id}/{kind}`); key = single `LIGHTSPEED_SECRETS_MASTER_KEY` per deployment (`multi-tenancy.md:96-99` — universe binding stops ciphertext transplant, but no per-tenant key; it encrypts secrets, not every row/blob).
- **Credential injection hidden from the model** (`docs/documentation/environments/credentials.md`): bindings map an env-var name to a stored secret/grant/provider key **by reference** (bindings "store references rather than secret values", :88); resolved just-in-time at process/job dispatch (:88-101); collision between a binding and explicit command `env` is **rejected** (:67-70); the API "exposes only the source handle, never secret material" (`api-reference.md:213-221`); the daemon keeps job credential values in memory and persists only variable names (:199-201). Named conflict checks exist too (e.g. `CLAUDE_CODE_OAUTH_TOKEN` vs `ANTHROPIC_API_KEY`, :136-140).
- **Output redaction at the daemon**: `crates/environment-daemon/src/redaction.rs:13-34` — literal secret bytes replaced with `<redacted>` in captured process/job output (repeated/adjacent handling, unit-tested). The docs are honest about limits: no coverage of transformed values, split-across-chunk values, files, or network egress — "use presence checks… rather than printing credentials" (:203-207).
- **Multi-tenant universes** (`deployment/multi-tenancy.md`): universe = tenant boundary enforced across API gateway (auth resolves a universe-bound service; no caller-supplied universe override, :18-25), Postgres (universe_id composite keys, :33-39), CAS keys (`<prefix>/universes/<uuid>/cas/…`, no cross-universe dedup, :40-45, :50-52), Temporal workflow IDs (`<universe-uuid>/<session-id>`, :42-47). **Honest limits**: no Postgres row-level security — DB/storage operators sit outside the boundary (:53-56); shared task queues give no per-tenant resource quotas (:57-62).
- **Trust-boundary honesty** (`overview.md:125-135`): "The daemon's access is the agent's access" — commands run as the envd OS user; cwd is "a convenience, not a process sandbox"; credential-bound processes can exfiltrate what they can read. Isolation is your VM/container/OS-user choice, not Lightspeed's.

### Comparison to our posture and what the demo/pilot can credibly claim

Ours: gitignored `.env` (user default: env vars/.env only), server-side **entire tool surface disabled** on every agent turn after the live bridge-mode leak was found and closed (BUILD_NOTES trial-gate finding 2 + verify-fix F2 `toolOverridesAllOff` asserted), reviewer deny lists with effective-permission tests, diff-by-value reviewers, sole-committer git.

Lightspeed's model is complementary, not competing: they keep secrets out of the *model-visible surface* (bindings inject at spawn; redaction masks captured output) — the same layer we already control, because our toolkit mediates all writes and runs all queues itself. What our demo/pilot needs to credibly claim isolation:

1. **Claimable today** (already built): no agent session can invoke git (boundary tests); reviewers have zero effective tools at config level plus server-side all-false tool maps at runtime; the model never sees secrets because queue/commit steps are toolkit code.
2. **Cheap upgrade worth stealing — output redaction**: anything entering an envelope attribute (captured diffs, tsc/vitest error text, tool output) passes a literal-secret redaction pass derived from the run's `.env` (S effort, mirrors `redaction.rs` semantics, with their documented limits as ours).
3. **Scoping the claim**: adopt their trust-boundary framing verbatim — harness-level isolation (tool-surface off, sole committer, diff-by-value) is *not* OS sandboxing; the pilot claim is "agents run as a dedicated user/container; secrets reach builds, never transcripts; evidence is redacted." Encrypted-at-rest for secrets (AES-256-GCM + AAD) is REJECT for v1 (we keep only `.env`), ADAPT for a paid pilot only if they require secrets at rest beyond env files. Multi-tenant universes: REJECT — single-tenant is our v1 contract; the AAD-binding *idea* is the only portable residue.

## 3. Fleet UI (React frontend, :5173)

Per-session, the session detail view renders: live **transcript** (`components/session/transcript-view.tsx` + `transcript-motion.tsx`, event-stream tail), **tool trace** (`tool-trace.tsx`), **run stats** (`run-stats.tsx:94-112`: context tokens, input/output totals, **cache-hit %** (`cachedInputTokens/inputTokens`), model-call count; "Unavailable" until full history loads — honest degradation), **run state machine** visible in the composer (`sending | queued | running | cancelled`, `SessionsPage.tsx:2127`), a **composer** that queues the next message while running, and approvals (`session/runs/approvals/decide`, `api-reference.md:178-185`: run resumes only after every pending approval has a decision).

Run control as API surface (`crates/api/contract/api-reference.md`):
- **cancel** (:169-176): in-flight model/tool activity aborted, **no grace turn**; returns projected state, terminal completion observed on the event stream.
- **steer** (:187-195): "Injects input into the named active run; the model sees it at the **next turn boundary** without interrupting the in-flight turn." Rejected for queued/cancelling/finished runs — a strict state machine, not a fire-and-forget.
- Sessions list (`pages/SessionsPage.tsx:199-341`): metadata key:value filters, closed/subagent toggles, deliberate **no bulk API** ("The API has no bulk operation by design", :328) with client-side fan-out per selected session.
- Fleet-adjacent pages: **BotsPage** with `StatusDot` + relative-time fleet sidebar (`BotsPage.tsx:16,140-205`); **EnvironmentsPage** polling provisioning/booting/closing status and desired-vs-observed **power divergence** (`EnvironmentsPage.tsx:62-63,114-115`, `components/environment/power-controls.tsx`, `idle-policy-dialog.tsx`); admin pages for universes/users/providers/keys.
- **In-browser demo engine** (`platform/web/src/demo/engine.ts:1-4`): a fixture-backed simulation producing the exact generated client contract shapes "so the real transcript reducer renders them unchanged" — `./dev.sh demo` runs the entire product UI with **no backend, no Docker** (`dev.sh:69-71`). This is how they screenshot/record demos without infra.

**Views worth stealing for our mission-control demo** (all are pure renders over streams we already persist — envelope tokens, queue burn-down, kill events — so they fit envelope-as-render):
1. **Run-stats tile** (context tokens / in+out / cache % / model calls per step-run). Our AC2 envelope already requires tokens for model roles; this is a read-only render, S effort, and it is the tile that makes cost legible to a VP during the video.
2. **Steer + cancel with visible run state machine.** Our kill/resume timeline proves durability; a steer box (durable attribute consumed at the next step boundary) and a cancel button (queue → blocked disposition) add a *live-control* beat to the re-recorded PHP→TS video. M effort (needs a durable steer attribute + envelope rule), highest demo payoff.
3. **Desired-vs-observed divergence display** (their power state pattern). Maps to our worktree grid: lease desired state vs reconciled state (epoch, base SHA, clean/dirty, poisoned). M effort; makes the reconcile table *visible* instead of documented.

## 4. Ops ergonomics

- **`./dev.sh`** (`dev.sh:1-90`): Node 24 gate; actions start/stop/down/reset/status; profiles `full | platform | runtime | demo`; installs deps, starts infra, applies migrations, waits for readiness checks; `--plan` prints the plan without executing. Platform applies its own migrations at startup; runtime profile needs one explicit `cargo run -p temporal-server -- migrate` (`docs/documentation/development/local-development.md:30-31,157-161`). `./dev.sh reset` recreates both DBs and clears the MinIO prefix (:186).
- **Compose** (`scripts/dev/docker-compose.yaml`): 4 services — postgres:17 (healthcheck), pgadmin, MinIO, Temporal `start-dev` with UI on :8233. The application itself never runs in compose; it runs as native processes under the launcher.
- **One backend binary** (`README.md:79`): every runtime role in one process or scaled as independent Temporal workers — with the **environment-gateway as a documented singleton** (`networking-and-ingress.md:22-29`). CLI (`crates/cli/`) is a separate multi-command client (session/env/vfs/profile/skills/mcp/auth subcommands).
- **Cancel/steer/fork UX**: strict state machines over the event log (see §3); fork & clone primitives live in the engine storage layer (`crates/engine/src/storage/session.rs`) — branch stored history or copy config without re-running.
- **Process discipline**: `docs/roadmap/pNNN-*.md` proposals with explicit Status headers (implemented/later), e.g. `p166-vfs-environment-transfer.md` — evidence-first, same spirit as our BUILD_NOTES exit scorecards.

### Comparison to our story

Ours: docker-compose is a **documented seam** (no official dex image; dex runs as a local binary, `BUILD_NOTES` environment table), `scripts/run-demo.ts` (worker/agent-roundtrip/recover-port verbs) + `scripts/chaos-kill.ts` with intent-before-kill sidecar, restart-into-recovery on the **same SQLite DB** (`dexcli dev -open=false -sqlite-db-filename …`, 0(b) evidence). Their reset-recreates-everything DX is *developer-convenient*; our restart-into-same-DB is *durability-honest* and AC1 depends on it — keep ours for the demo, steal the launcher ideas: a `status` verb (readiness checks across dex/opencode/worker/dashboard) and a `--plan` dry-run are S effort on `run-demo.ts`.

### Headline ruling: substrate vs patterns

**lightspeed is a REJECT-as-substrate.** Running our workload on it means discarding dex (Temporal replaces dex's durable-step engine), opencode (their `llm-runtime` replaces the harness), TypeSafe (their deterministic-core/Jev-shaped judgments live in Rust), and the all-TypeScript constraint — a pivot, not a port. It also re-bases our evidence story on their event log rather than our envelope stream, voiding the Phase 0–5 kill/reconcile evidence already banked (BUILD_NOTES: 0(a)–0(h) all PASS, trial gate, Phases 3–4). Nothing about their substrate is *required* by a hosting-constrained shop: Postgres+MinIO+Temporal is 3 infra services where ours needs one binary and a compose seam.

**Its value is portable patterns. The three takeaways:**
1. **Dial-home compute**: orchestrator-listens, machines-dial — the credible multi-machine answer for a no-inbound, no-cloud shop (claim in demo, build in v2).
2. **Secrets never touch the model surface**: reference-bound injection at the spawn boundary + literal redaction of captured output — adoptable in days on our envelope write path, and it turns our `.env` discipline into a demonstrable, VP-legible security claim.
3. **Live run control as a strict state machine**: steer-at-turn-boundary, cancel-without-grace, approvals gate — each a durable attribute + render on our stack; this is what makes the re-recorded demo video show a *controlled* fleet, not just a surviving one.

Consistent with the ODW ruling (`.omc/plans/2026-09-25-porting-toolkit-consensus.md` :197): evaluate neighbors for patterns, keep the substrate.
