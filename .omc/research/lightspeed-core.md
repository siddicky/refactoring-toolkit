# Research: lightspeed (siddicky fork of smartcomputer-ai/lightspeed) — deterministic core & durability architecture

- **Evaluated**: 2026-09-25, clone at `/tmp/ls-core` (shallow, default branch). Focus: `crates/engine` (core FSM), `crates/temporal-workflow` (durable host), `crates/store-pg`/`store-fs` (log + CAS storage), `docs/documentation/how-it-works/`.
- **Lane**: deterministic core & durability (lane "ls-a"). Baseline: `.omc/plans/2026-09-25-porting-toolkit-consensus.md` + `BUILD_NOTES.md` (Phase 0 a–h all PASS; trial gate, Phases 3–4 evidence recorded).
- **Upstream**: Apache-2.0, Rust + Temporal (temporalio Rust SDK 0.4.0, pre-GA) + Postgres/S3 CAS. "Run thousands of agents... durable workflows" — sessions run months; the agent loop is a lightweight durable workflow, machines attach only when needed.

## TL;DR

Lightspeed independently arrived at the same constitutional shape we did — **pure decide → CAS append → pure reduce → effect intent → adapter** — but with sharper edges in three places we should steal: (1) the session log append is a CAS compare-and-swap against the log head with an idempotent repeat protocol, (2) a three-layer history-hygiene stack (event log authoritative / reducer checkpoints as accelerators / ContinueAsNew rollover with CAS-offloaded payloads) that keeps month-long sessions healthy, and (3) steer-while-running via an admissions channel raced against in-flight activities, with turn-request freezing by revision fingerprint. Temporal is a swappable host, not the source of durability — they ship a substrate-neutral runner with no Temporal dependency, which settles our dex-vs-Temporal question: **REJECT Temporal as substrate, ADAPT the patterns**. Our ADR ("script→dex-compiler coherent, interpreter never") is unchanged; the drive-machine shape is the compilable target, not an interpreter.

## 1. Event-sourced deterministic core

### What the session log contains

Every session is one append-only log of typed entries (`crates/engine/src/session/stored.rs:12-17`):

```rust
pub struct SessionEntry<E, J> {
    pub position: SessionPosition,   // { seq: EventSeq } — strict seq+1
    pub observed_at_ms: u64,         // time is PASSED IN, never read (docs:31-33)
    pub joins: J,                    // BTreeMap<String,String>: run_id/turn_id/batch/call correlation
    pub event: E,                    // StoredEvent { kind: "lightspeed.run.started", version, payload }
}
```

Event vocabulary is a **closed FSM** (`crates/engine/src/core/mod.rs:3-5`): Lifecycle, Run, Approval, Turn, Context, Environment, ToolConfig, Tool, Promise, WorkflowTool* — dispatched by the pure reducer `apply_event` (`crates/engine/src/core/apply.rs:5-30`), which hard-fails `DomainError::EventOrdering` on any seq gap. The log carries facts only: config changes, accepted runs, turn outcomes, tool results, approvals, promises. **Payloads are references, not bytes** — `BlobRef = "sha256:<64hex>"` + `ContentRef{content_ref, media_type, provider_kind}` + bounded preview (`crates/engine/src/blob.rs:12-25`; doc: `docs/documentation/how-it-works/context-and-storage.md:16-27`).

### The decide→append→reduce→act loop (effect intents, precisely)

- **Admission** (pure): `admit_command(state, command, observed_at_ms) -> Vec<CoreAgentEventProposal>` validates against current state, rejects, or de-duplicates (`crates/engine/src/core/admit.rs:15-19`). Duplicate `submission_id` with identical content resolves to the already-accepted run; different content is rejected (docs agent-loop:215-218) — their op-ID analogue.
- **Planning** (pure): `plan_next` consults approval → run → tooling → context → turn planners in fixed order (`crates/engine/src/core/planning.rs:10-24`).
- **Effect intents** = `CoreAgentAction` (`crates/engine/src/core/drive.rs:32-51`): `AppendEvents { expected_head, events }` | `GenerateLlm { request }` | `CompactContext { request }` | `InvokeTools { request }` | `Idle` | `Closed` | `StepLimitReached`. The drive machine does **no I/O at all** (`drive.rs:1-7`): "Local runtimes and workflow substrates fulfill emitted actions and resume the drive with committed entries or execution results."
- **Append is CAS**: every append action carries `expected_head = drive.head` (`drive.rs:399-417`). The storage activity commits; Postgres does `SELECT ... FOR UPDATE` and returns `ExpectedHeadMismatch` on divergence (`crates/store-pg/src/session.rs:50-87`). Only then does the reducer apply the returned entries (`drive.rs:142-155`) — commit-before-apply, always.
- **Adapters**: `CoreAgentLlm` / `CoreAgentTools` traits over serializable request/result records (`crates/engine/src/core/io.rs:2-12`). The workflow never holds async adapters; it fulfills the action values.

### Determinism vs provider nondeterminism (their answer to our hardest problem)

The invariant: **the model's output is committed exactly once, as events; replay never re-derives it; re-generation is a whole-turn re-execution.**

1. Turn is planned → `TurnEvent::Planned { request_fingerprint, config_revision, context_revision, toolset_revision }` commits first (`crates/engine/src/core/drive.rs:539-547`).
2. The LLM request is a **deterministic function of committed state**, and this is enforced, not assumed: `build_planned_llm_request` re-derives the request and hard-fails unless model/config/context/toolset revisions AND the recomputed `request_fingerprint` all match the plan (`crates/engine/src/core/components/llm.rs:187-220`, fingerprint built at llm.rs:162-170). If the worker dies between plan and provider call, `rebuild_llm_request_for_planned_turn` reconstructs the exact request from the log (`drive.rs:533-573`) and re-sends it.
3. The generation activity runs outside; its result is converted to proposals (context entries + `GenerationCompleted` + approvals + `Turn::Completed`) and committed once with expected_head CAS (`drive.rs:590-657`). Killed mid-generation → activity retries → a *fresh* model output is committed. Divergent content across attempts is accepted and simply recorded — determinism is a claim about control flow, never about content. This is semantically identical to our "killed agent steps are atomic re-executable only as a whole" (our 0e/kill-during-write evidence), just stated as a turn boundary instead of a step boundary.
4. Docs state the honest limit explicitly: "Deterministic replay and external exactly-once execution are different claims. If a remote service performed an operation but its response was lost... Stable operation IDs, appropriate provider idempotency, and effect-specific recovery are still necessary" (`docs/.../agent-loop-and-durability.md:228-233`). Same conclusion as our sole-committer ADR.
5. Storage-side idempotency mirrors our op-ID commit: "The storage activity recognizes an exact repeat at the expected position by comparing the already committed entries, including their sequence and event contents. It can return that committed result instead of appending duplicates. A conflicting append remains an error" (`docs/.../agent-loop-and-durability.md:207-213`).
6. Tool batches commit **progressively per call**: "each terminal result appends durably on its own, a failed call never re-runs a completed sibling" (`drive.rs:192-223`). Retry policy is per-effect: read-only/retry-safe tools get bounded retries; everything else gets ONE attempt (`docs/.../agent-loop-and-durability.md:219-226`).

The Temporal host loop is a thin shell over this (`crates/temporal-workflow/src/workflows/session/drive.rs:116-189`): `next_action_unbounded → match action → AppendEvents via activity / GenerateLlm via raced activity / InvokeTools / Idle`, with admissions drained at **every action boundary** and the plan recomputed.

## 2. Month-long sessions: history hygiene stack

Three layers, each with a distinct contract (doc: `agent-loop-and-durability.md:107-126` "There are two histories"):

| Layer | Records | Reconstructs |
|---|---|---|
| Session log (Postgres/FS + CAS) | domain facts | agent state + client-visible history |
| Reducer checkpoints | reduced state at seq N (CAS blob; "disposable pointer", log authoritative) — `crates/engine/src/storage/session.rs:243-244` | fast recovery; "accelerators, not a second source of truth that can silently override the log" (docs:152-154) |
| Temporal history | signals, activity results, timers, patches | execution of the coordinating workflow code |

Mechanisms:

- **Bootstrap/rehydrate reduction happens in an activity, not in-workflow.** Their post-mortem: "Previously the workflow pulled every persisted entry through the activity result and reduced in-workflow; that transported the full log through Temporal history and **failed long-lived sessions**. The reduction now happens inside the activity... and only the compact result crosses the boundary" (`crates/temporal-workflow/src/rehydrate.rs:1-9`). Checkpoint + tail replay uses the *same* accumulator as from-seq-1 replay (`rehydrate.rs:61-78`) — identical reducer semantics by construction. Missing checkpoint = performance issue; missing events = correctness failure (docs:143-145).
- **ContinueAsNew rollover**: due when Temporal suggests it or `history_length >= 10_000` (`crates/temporal-workflow/src/config.rs:12`; `workflows/session/wait_loop.rs:109-165`). Rollover waits for a **safe committed boundary** — all pending admissions/emissions/resumes/backoffs drained (`wait_loop.rs:127-138`) — and can happen mid-run: parked batches and durable promises survive because their facts are already session state; the active run wakes without a user message after rehydrate (`docs/.../agent-loop-and-durability.md:156-183`). Replay-compatible code deploys use Temporal patch markers (`drive.rs:269-273`).
- **Payload offload, both directions**: "Activities instead write payloads to CAS and return references plus the facts needed for branching. A later activity loads the content when constructing its request" (`docs/.../context-and-storage.md:225-243`). What stays inline in events: small previews, token estimates, kinds, refs. Inline-vs-offloaded cutoff in the hosted store: **≤64 KiB inline in Postgres; larger requires object storage** (`context-and-storage.md:250-253`).
- **Retention correctness**: appending events records their canonical content refs as session *roots* **in the same transaction**; an append referencing a missing blob is *rejected* (`context-and-storage.md:293-295`; FK-backed roots/holders in `crates/store-pg/src/cas_sweep.rs:1-11`). Hourly bounded collector, 7-day grace, incarnation-specific object keys so re-upload of identical bytes can't be collaterally deleted (sweep + `blob_cache.rs:1-13` positive-only immutable cache). Compaction never releases roots — "Reducing a model window and reclaiming disk space are separate operations" (`context-and-storage.md:312-317`).
- **Context compaction** is explicit, event-sourced, lossy-on-context-only: `CompactionPolicy::ProviderStandalone { compact_threshold_tokens, target_tokens }` (`crates/engine/src/core/components/config.rs:583-595`); only fires with no active/queued run; refuses if any required token estimate is missing (never substitutes provider usage) (`components/context.rs:762,791`; docs:197-202); a stale compaction result cannot rewrite a newer context revision; original events remain in history. Request-prefix caching is protected by keyed catalogs appended at the tail with ≤5 superseded versions retained (`context-and-storage.md:132-165`).

**Compare to our envelope stream + dispatch-log anchoring**: our AC2 evidence chain is anchored to dex's dispatch log (0h PASS) and envelope events in attributes. At demo scale that's fine; at month scale we would hit exactly their three failure modes: unbounded attribute growth per flow, fat step payloads (our diffs travel by value), and full rehydrate from seq 1. Their fix set maps onto us as: (a) treat envelope events as refs+previews with diffs over a size cutoff going to CAS/git objects (we already have a natural CAS — the project repo's object store; keyed commits already give content-addressing), (b) keep the dispatch log as the authoritative "session log" analogue — it already is — and treat any renderer-side snapshot/cache as accelerator-only, and (c) our flows are per-file bounded with round caps, so we need rollover far less; where it *would* bite is a month-long multi-fixture campaign (v2 scale knob).

## 3. Session fork & clone; cancel/steer

### Fork & clone (storage-layer semantics)

- **Clone = config-only re-open**: replay source state, then `core_agent_clone_opening_events` materializes `Opened{config}` + managed workflow-tool bindings + non-system tools + active environment as the *new* session's opening events; lifecycle-managed sessions refuse (`crates/engine/src/core/session_graph.rs:26-38`). `CreateClonedSession` persists those opening events (`crates/engine/src/storage/session.rs:181-188`).
- **Fork = shared log prefix**: `CreateForkedSession { source_seq }` — child inherits the source log's prefix `[1..source_seq]`, then appends its own (`storage/session.rs:190-198`). **Fork points are run-boundary-safe**: `validate_fork_point` rejects any seq inside a non-terminal run's range; `largest_safe_fork_seq` = just before the earliest open run (`storage/session.rs:1203-1264`). Retention root is inherited by forks; deletion of a closed source refuses while a fork child still inherits its history (`storage/session.rs:37-46,492-505`).
- **Subagent spawn** is a third shape: `SessionOrigin { parent_session_id, parent_run_id, root_session_id, depth, limits (parent's grant attenuated by parent's own origin limits, pinned at spawn) }` (`storage/session.rs:54-79`) with root-scoped limits MaxDepth/MaxDescendants/MaxConcurrent.
- Status: "The current public clients do not expose fork/clone creation as ordinary RPC operations" — storage capabilities today (`docs/.../context-and-storage.md:276-281`).

### Cancel & steer while running

- **Admissions taxonomy** (`crates/temporal-workflow/src/workflows/session/admissions.rs:169-257`): run-control commands — `CancelRun`, `ForceCancelRun`, `RequestRunSteering`, `DecideApproval`, `RequestRun`, `ResolvePromise`, `ResumeToolBatch`, `CloseSession` — are **admissible mid-turn**; context/config/tool mutations are **held back** because "That turn's request is frozen at its planned revisions and the runtime re-derives it from state, so those revisions must not move until the turn completes."
- **The race primitive** (`crates/temporal-workflow/src/workflows/session/control.rs:31-93`): in-flight activity `select!`-raced against `wait_condition(has_admissible_admissions)`; after each drain, `still_wanted(state)` re-checks against live engine state; if false → `activity.cancel()` (TryCancel; the worker learns via heartbeat) → `Raced::Preempted` → caller re-plans from the drive. Cancel changes authoritative run state and requests cancellation of activities/owned work; "neither that watchdog nor an API acknowledgment reverses a remote operation that already happened" (`docs/.../agent-loop-and-durability.md:198-203`).
- **Steering** = first-class run input: steering input entries are materialized as context entries tagged with `steering_id` (`crates/engine/src/core/components/context.rs:868-888`), marked `consumed_by_turn_id` when the next planned turn's request includes them (`context.rs:450-457`), and — the sharp edge — **"A final-output turn does not end a run while such steering exists — the run gets one more turn that carries it, so 'steer' never silently does nothing"** (`crates/engine/src/core/components/run.rs:416-425`).
- **Cancel watchdog**: a run stuck in `Cancelling` past 60 s is force-completed (`crates/temporal-workflow/src/workflows/session/watchdog.rs:6,55-87`); "A missed edge in the cancellation state machine must degrade to a forced transition, never a permanent wedge." `ForceCancelRun` is an idempotent no-op when already terminal, so racing a late normal cancel is harmless.

**Compare to our fencing** (epoch bump → abort+confirm → lease reclaim → reconcile → re-dispatch; abort≤3 → poisoned/blocked): our kill-and-redo is the *recovery* story; theirs adds a *control* story — steering a live run without killing it. That is genuinely the thing our porting loop lacks and wants: a stuck implementer (wrong direction, rambling, tool-looping) currently costs a whole kill cycle + epoch bump + reconcile; with their shape we would append a steer directive as a durable attribute and let the *next round* carry it, with a durable counter ensuring the round actually consumes it (their unconsumed-steering rule translated: a round cannot complete as clean while an unconsumed steer exists). Our frozen-revision analogue already exists implicitly — the diff captured by value before review — but we should make the "review/fixer planned against diff revision N" binding explicit. Our epoch+abort remains *stronger* for the SIGKILL case (they assume the workflow host survives or replays; we prove recovery when it doesn't); their watchdog is the better answer to our "abort retried ≤3 → poisoned/blocked" terminal — force-disposition after a deadline, recorded honestly in the evidence stream.

## 4. Why Temporal (Rust SDK) — does it move our dex calculus?

**No. REJECT Temporal-as-substrate; ADAPT patterns. The ADR stands.**

Decisive evidence that Temporal is incidental to their durability:

1. The core is **substrate-neutral by construction** (`drive.rs:1-7`), and they *ship a second host*: `crates/test-support/src/runner/drive.rs` is a plain-loop `SessionRunner` fulfilling the same actions through trait adapters with **no dependency on the Temporal workflow crate**. Temporal buys scheduling ergonomics (signals≈our durable mini-steps for admissions, timers≈durable steps, activity retry/heartbeat≈envelope heartbeats we already run, ContinueAsNew≈their rollover, patch markers), not the durability itself — the CAS append + reducer does that.
2. The Rust SDK is pre-GA (`temporalio-*-0.4.0`, `crates/temporal-workflow/Cargo.toml:21-25`) and the integration is *large*: 8.3k lines in `workflows/session/` alone plus a server wrapper crate (`crates/temporal-server`) — vendor-heavy seam, the exact thing our "vendor-thin seams" principle forbids. Adopting it would mean a Rust toolchain + Temporal server for a toolkit whose every other dependency is TS.
3. Our ADR's real clause — "**script→dex-compiler coherent, interpreter never**" — is *reinforced*: lightspeed is the existence proof that a fixed, closed command/event vocabulary with pure admission/planning/reduction compiles cleanly onto a durable step host. That is precisely the shape a dex-compiler target wants: their `CoreAgentAction` enum maps 1:1 onto durable steps (AppendEvents→attribute-batch record step with CAS reconcile; GenerateLlm→our envelope agent step; CompactContext→durable compaction step; InvokeTools→toolkit-owned queue steps). Nothing here re-opens the interpreter question.
4. What we should copy from their Temporal usage is *host-agnostic*: patch-marker discipline (their `ctx.patched(...)` before new code paths, `drive.rs:269-273`) ≈ our pinned-dex-version + retained kill-test regression strategy, already in the plan; deterministic recompute-verify (`build_planned_llm_request`) as a resume assertion; and the machine-readable contract export with known-answer vectors (`workflow_contract.rs:1-13`) ≈ our envelope-schema test fixtures.

## Cross-lane observations for the consensus record

1. **Convergent evolution validates the plan.** An independent production system with month-long sessions uses the same constitutional moves we chose: sole-committer-style operation IDs, commit-preserving recovery ("conflicting append remains an error"), evidence as pure projection over the log (`api-projection` crate is explicitly "the explicit bridge between reducer internals and the stable client-facing API... does not admit commands or execute side effects" — `crates/api-projection/src/lib.rs:1-4`), and time passed in, never read. Confidence in our architecture should be raised accordingly.
2. **Their sharpest idea we lack is turn freezing.** Freezing (config, context, toolset, request-fingerprint) revisions at plan time and *verifying on rebuild* is a cheap, total answer to "what state did this in-flight step assume" — it upgrades our fencing from abort-and-reconcile to detect-and-refuse for the non-kill skew cases.
3. **Their sharpest idea we already have is honest limits**: "Deterministic replay and external exactly-once execution are different claims" is our ADR consequence section in one sentence — worth quoting verbatim in the toolkit docs when we write them (v2, per non-goals).
4. **Their post-mortem is our risk table's prophecy**: rehydrate-in-workflow "failed long-lived sessions" is exactly our "attribute growth at scale" risk; adopt the boundary rule (compact result across the seam, never the raw log) in any Phase 5+ dashboard/metrics aggregation.
